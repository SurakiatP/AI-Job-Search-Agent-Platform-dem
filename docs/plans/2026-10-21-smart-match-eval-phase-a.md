# Smart match evaluation harness (Phase A) — implementation plan

Spec: docs/superpowers/specs/2026-10-21-smart-match-accuracy-design.md (FR-SM-01..03, AC-SM-01..03, D-01..D-04). Worktree branch: feat/smart-match-accuracy.

## Global Constraints
- Everything lives under `backend/tests/smart_match_eval/` (plain modules, no import from the app except `job_search_platform.services.smart_match` and `job_search_platform.integrations.jev`). No change to product code.
- Live provider calls only when env `SMART_MATCH_EVAL_LIVE=1`; pytest and CI never call a provider. API keys come from env vars (`OPENROUTER_API_KEY`) and are never printed, logged or stored.
- All CVs and job postings are synthetic and contain no real person, company or contact data (use fictional company names, `@example.test` style emails if any contact is needed).
- Deterministic: fixed fixtures, temperature 0 for the judge, results cached on disk under `backend/tests/smart_match_eval/.cache/` (git-ignored) keyed by sha256 of (model, inputs).
- Tests first: write the failing test, see it fail for the right reason, then implement. Unit tests run offline with fakes. Python 3.12, existing deps only (no numpy/scipy: implement the metrics in pure Python).
- Label scale: `good` = 2, `maybe` = 1, `no` = 0. Metric names: `spearman`, `ndcg_at_10`, `precision_at_10`, `kappa`.

## Task 1: metrics module
Create `backend/tests/smart_match_eval/metrics.py` and `backend/tests/unit/test_smart_match_eval_metrics.py`.
Functions (pure): `spearman(xs, ys)` with average ranks for ties, returns 0.0 if either side is constant; `ndcg_at_k(relevances_in_ranked_order, k=10)` using gain `2**rel - 1` and `1/log2(i+2)`, returns 0.0 if ideal DCG is 0; `precision_at_k(relevances_in_ranked_order, k=10, threshold=2)`; `cohen_kappa(a, b)` for equal-length label lists, returns 1.0 when both lists are identical and constant, else standard kappa.
Tests with hand-computed values: spearman([1,2,3],[1,2,3])==1.0, reversed == -1.0, ties case; ndcg of a perfect ranking == 1.0 and of a hand-computed imperfect ranking (state the arithmetic in the test); precision_at_k with fewer than k items divides by the number of items; kappa on a 2x2 hand example equals the hand value (e.g. a=[1,1,0,0], b=[1,0,0,0] -> 0.5) and kappa for identical labels == 1.0.

## Task 2: synthetic fixtures
Create `backend/tests/smart_match_eval/data/cvs.json` (10 CVs) and `data/pairs.json` (60 pairs), plus `backend/tests/unit/test_smart_match_eval_fixtures.py`.
CVs: 10 fictional candidates, 5 role families (software/data engineering, marketing, accounting/finance, nursing/healthcare admin, operations/logistics), 2 per family, 6 Thai and 4 English, mixed seniority (junior, mid, senior). Each CV is plain text of 150-300 words with roles, years, skills, education. Fields: `id` (cv-01..cv-10), `language`, `text`.
Jobs: written inline in `pairs.json` as objects with the same keys `smart_match` expects: `slug` (unique, <=200), `title`, `company` (fictional), `description_markdown` (80-200 words, Thai or English, states required and preferred skills and years), `skills` (list of strings). Each pair: `cv_id`, `job` (object), `label` (`good`|`maybe`|`no`), `reason` (one line), `kind` (`clear` or `ambiguous`). Counts: 60 pairs total, 20 good / 20 maybe / 20 no; exactly 10 pairs have `kind == "ambiguous"` (deliberately borderline: adjacent field, seniority off by one level, one missing must-have); every CV appears in at least 5 pairs and in at least one good and one no pair.
Labels are by construction: write the job so the label is true for that CV (good = same role family and level and the must-haves present; maybe = adjacent or one clear gap; no = different field or hard blocker such as a required licence the CV lacks).
Tests: schema and counts above, unique slugs, every `cv_id` exists, label values valid, no `@` characters other than `@example.test`, no digits sequences that look like phone numbers (regex `\d{9,}` absent).

## Task 3: scoring runner
Create `backend/tests/smart_match_eval/run_eval.py` and `backend/tests/unit/test_smart_match_eval_run.py`.
`score_pairs(pairs, cvs, client, cache_dir)` scores each pair exactly as the worker does: `skills = smart_match.job_skills(job)`, `answers = client.decide(smart_match.job_state(cv_text, job), smart_match.job_questions(skills))`, `result = smart_match.combine(answers, skills)`; returns list of dicts with `cv_id`, `slug`, `fit_percent`, `label`, `kind`. Cache results on disk by sha256(model + json of state + questions).
`evaluate(scored)` groups by CV, ranks that CV's jobs by `fit_percent` descending (ties by slug), and returns macro-averaged `ndcg_at_10` and `precision_at_10` over CVs, the Spearman between `fit_percent` and label value over all pairs, and a confusion table of `smart_match.band(fit)` (1-5) against label counts.
`main()`: refuses to run unless `SMART_MATCH_EVAL_LIVE=1`; builds `JevClient(os.environ["OPENROUTER_API_KEY"])`; prints the four metric lines, the confusion table, the number of live calls made and elapsed seconds; exits non-zero with a clear message when the env vars are missing. Run as `python -m backend.tests.smart_match_eval.run_eval` or `python backend/tests/smart_match_eval/run_eval.py`; document the command in `backend/tests/smart_match_eval/README.md` (one short page: purpose, env vars, cost note, how to read output).
Tests (offline, fake client returning canned answers shaped like Jev answers: `role_fit` {"score": 0..3, "confidence"}, `seniority_fit` {"probabilities"}, `hard_blocker` {"noul"}, `skill_i`/`must_i` {"noul"}): scoring order and metrics on a tiny hand-built set with known expected values; cache hit makes zero second-run client calls; `main()` exits non-zero without `SMART_MATCH_EVAL_LIVE`; the repo has no test that imports a real network client (assert the fake is used).

## Task 4: judge and owner sheet
Create `backend/tests/smart_match_eval/judge.py` and `backend/tests/unit/test_smart_match_eval_judge.py`.
`judge_pairs(pairs, cvs, post, cache_dir)` where `post(payload: dict) -> dict` is an injected HTTP function (default: POST to `https://openrouter.ai/api/v1/chat/completions` with model `deepseek/deepseek-v4.1-flash-1017`, temperature 0, `Authorization: Bearer` from `OPENROUTER_API_KEY`, 60 s timeout, no redirects, no env proxies). Prompt asks for a JSON object `{"label": "good|maybe|no", "reason": "<one line>"}`; parse strictly, one retry on malformed output, then record `label: null`. Cache by sha256 of the payload.
`kappa_report(judged, owner_labels)` returns kappa of judge vs construction labels (all pairs) and vs owner labels (only the pairs in `owner_labels.json`, a dict `slug+cv_id -> label`, optional file); `disagreements(judged, scored)` lists pairs where judge label, construction label and Jev band (band>=4 means good, 3 maybe, <=2 no) are not all equal, capped at 25, as plain dicts.
`owner_sheet(pairs, count=15)` prints a Markdown sheet for the owner: 15 pairs chosen deterministically (seeded, 5 per label, at least 3 ambiguous) with CV text, job text and an empty `Your label: ___` line, WITHOUT showing the construction label or the judge label.
`main()` requires `SMART_MATCH_EVAL_LIVE=1` for judging; subcommand `sheet` runs offline. Add a short "judge" section to the README including the acceptance rule from decision D-03 (kappa vs owner >= 0.6).
Tests (offline, fake `post`): parse success and malformed-then-retry, label null after two failures, cache prevents a second post, kappa values on a hand example, disagreements cap and content, owner sheet has exactly 15 pairs, is deterministic, and never contains the strings of the construction labels' `reason` fields; the API key value never appears in any returned or printed output (use a sentinel key in the test).
